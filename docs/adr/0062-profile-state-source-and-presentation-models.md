# Separate the Profile state source from observable presentation Models

UDF and a single source of truth require shared data to have one owner and a controlled update path. Keep the Profile's data in the UI-independent `DenApplication` package, with read-only `DenStateStore` snapshots and a separately held write capability. Keep persisted Domain values unchanged. Native resources and persistence callbacks stay outside this core. The shared Store uses Swift Observation directly; this standard framework dependency is accepted to avoid a custom notification bridge while keeping SwiftUI and Presentation dependencies out of Application.

Move the Store-independent Drawer, Notifications, Overview, Desk Filter, Open Board, zmx Sessions, and Window Models into `DenPresentationModels`, which depends only on Domain values and Observation. Use Model names for their presentation role, and `DenWindowModel` for window presentation. App composition supplies live data and operations. Window state, effects, confirmation display values, feedback, and input intents belong to Presentation; App adapters translate or execute the requested operations. Presentation Models do not import SwiftUI; Views apply animations to their observable state changes. This enforces the extracted dependency boundaries without duplicating the authoritative shared state or creating a Store per Feature. Native workflows and window operations remain in the app target.

Extend this layer boundary to independent operations in `DenApplication` and persistence/native implementations in `DenInfrastructure`. App composes their concrete bindings. Application contains Board input interpretation, opening decisions, and pure Board/Desk state transformations. Board opening decisions are returned as values, including the optional Recent item; the decision code does not invoke Controller insertion, Recent recording, or Tutorial actions. The Profile-owned BoardCreation operation executes Board creation and writes insertion/Recent updates to the same shared source. BoardRemoval executes removal/restoration and their transient history using that source. DeskLifecycle, DeskUpdates, DeskMovement and DenReset likewise update the same source while App retains window assignment, confirmations and native cleanup. Each call supplies its target and synchronous notification destination; the shared operation retains no window or Model. App composes persistence and translates creation notices into native resource connections and window effects. Controller still coordinates unmigrated operations. Feature groups classify responsibility within these modules rather than recreating every layer under each Feature; current placement and extraction progress are described in the architecture guide.
